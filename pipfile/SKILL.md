# pipfile

<!-- markdownlint-disable MD013 MD023 MD031 MD032 -->

## When to Use
- When creating or editing `Pipfile` TOML structure for Python project dependency management.
- When reviewing `Pipfile.lock` content to verify hash integrity and pinned versions.
- When migrating from `requirements.txt` to `Pipfile` format for deterministic dependency resolution.
- When updating the `Pipfile` to add, remove, or modify dependency entries while following TOML syntax.
- When separating production (`[packages]`) and development (`[dev-packages]`) dependencies in the `Pipfile`.
- When debugging dependency resolution conflicts by inspecting the locked versions in `Pipfile.lock`.

## When Not to Use
- When you need to actually install packages or run commands within the environment — load the **pipenv** skill instead, which handles environment operations.
- When working with Poetry's `pyproject.toml` or Conda's `environment.yaml` — this skill is specific to `Pipfile`/`Pipfile.lock` format only.
- When the project does not use `Pipfile` at all — use the appropriate dependency management skill for the project's format.
- When only reading dependency versions without editing — `pipenv graph` or `pipenv run pip list` may be simpler than parsing the lockfile.

## Common Pitfalls
- `Pipfile.lock` MUST NEVER be edited manually — it is auto-generated by `pipenv lock` and manual edits will be overwritten or cause hash mismatches.
- The `Pipfile` uses standard TOML syntax — invalid TOML (e.g., unquoted strings with special characters, incorrect table headers) will break `pipenv` commands.
- Source URLs in the `[[source]]` section must be trusted indexes — using untrusted or custom PyPI mirrors can introduce security risks.
- When both `Pipfile` and `requirements.txt` exist, they can drift out of sync — prefer one canonical source and keep them aligned if both are required.

Use this skill for managing the structure and content of `Pipfile` and `Pipfile.lock` files.

## Core Process

1. **Structure Definition**: Define the `Pipfile` structure including source, packages, and dev-packages.
2. **Locking**: Ensure all dependencies are pinned in `Pipfile.lock` using deterministic hashing.
3. **Manual Edits**: Manually editing the `Pipfile` is allowed but must adhere strictly to standard TOML syntax.

## Core Principles

- **Deterministic Environments**: Rely on `Pipfile.lock` to guarantee exact versions and hashes. Never edit `Pipfile.lock` manually.
- **Group Separation**: Strictly separate production (`[packages]`) and development (`[dev-packages]`) dependencies.
- **TOML Compliance**: Manually editing the `Pipfile` is allowed but must adhere strictly to standard TOML syntax. Prefer CLI commands over manual edits when possible.
- **Security-First**: Utilize `Pipfile.lock`'s stored hashes to prevent supply-chain attacks. Regularly run vulnerability scans.
- **CI/CD Invariance**: Use `--deploy` to ensure `Pipfile.lock` is up-to-date and fails if not. Use `--system` when running in Docker containers.

## What to Avoid

- **Interactive Subshells**: As an automated agent, you MUST NOT run `pipenv shell`.
- **Manual Lockfile Edits**: NEVER manually edit `Pipfile.lock`.
- **Using requirements.txt blindly**: Migrate dependencies to the `Pipfile` structure instead of using legacy formats.
